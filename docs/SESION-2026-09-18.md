## 2. Marco normativo: los plazos reales

VeriFactu **no es obligatorio todavía**. El **Real Decreto-ley 15/2025, de 2 de diciembre**
(BOE de 3-dic-2025) aplazó **por segunda vez** la entrada en vigor del RD 1007/2023.

| Obligado | Fecha límite de adaptación del SIF |
|---|---|
| Sujetos al **Impuesto sobre Sociedades** | **1 de enero de 2027** |
| **Resto** de obligados (autónomos / IRPF) | **1 de julio de 2027** |

El periodo anterior a esas fechas es, en palabras de la propia AEAT, un **periodo de pruebas**:
se pueden remitir registros de prueba con un SIF en modalidad VERI\*FACTU y seguir facturando
con otro SIF hasta la fecha límite.

Lo que sí venció es la obligación de los **productores de software** (9 meses desde la Orden
HAC de 29-jul-2025), que aplica a Odoo S.A., no al taller.

Quedan **excluidos** los obligados a **SII** y los territorios forales con TicketBAI.

**Pendiente de dato:** si el taller es **SL** → enero 2027; si es **autónomo** → julio 2027.

Fuentes:
- [AEAT — Nota informativa: ampliación del plazo de adaptación de los SIF](https://sede.agenciatributaria.gob.es/Sede/iva/sistemas-informaticos-facturacion-verifactu/nota-informativa-ampliacion-plazo-adaptacion-facturacion.html)
- [BOE-A-2025-24446 — Real Decreto-ley 15/2025](https://www.boe.es/buscar/doc.php?id=BOE-A-2025-24446)

**Regla derivada:** la fecha de obligatoriedad se ha movido dos veces. No afirmarla de memoria
en ninguna sesión futura; verificar contra la AEAT.

                      No hay un certificado configurado para Veri*Factu en la compañia."

El módulo **crea el registro igualmente**, en estado fallido y con el error persistido, en vez

### Qué queda verificado

Todo lo que no depende del certificado: datos fiscales, cálculo de IVA sobre líneas tecleadas,

### Limpieza posterior y la cadena inmutable

Los datos de prueba se borraron al terminar: factura `INV/2026/00004`, orden `B012`, vehículo
`4821KDR`, cliente ficticio y el certificado. La compañía volvió a `My Company` sin NIF y con
Veri\*Factu desactivado.

**Un registro no se pudo borrar, y es por diseño.** El módulo lo impide:

```python
# verifactu_document.py:183
def _never_unlink_chained_documents(self):
    raise UserError("You cannot delete Veri*Factu Documents that are part
                     of the chain of all Veri*Factu Documents.")
```

La cadena de registros es **inmutable**: cada uno lleva la huella del anterior, así que poder
borrar uno la invalidaría como prueba. Odoo lo bloquea aunque seas administrador.

Queda por tanto en `taller` un registro huérfano (`id=2`, `chain_index=1`, `rejected`, sin
factura asociada), y la secuencia de encadenamiento con el nombre de la compañía ficticia.
**Decisión: se dejan.** Borrarlos requeriría SQL directo, saltándose a mano una salvaguarda
legal; en una BD de desarrollo no compensa.

> **Consecuencia para el despliegue.** Esta base de datos ya tiene un registro de prueba dentro
> de la cadena. Si producción se montara clonando `taller`, la primera factura real encadenaría
> sobre un registro rechazado de una empresa que no existe. **Producción debe nacer de una BD
> limpia**, nunca de un volcado de `taller`. Antes era higiene; ahora hay un motivo técnico
> concreto.

## 6. Deuda de la sesión del 17-sep: el bug IDNA del configurador web

Se quedó sin documentar. El código estaba en el árbol sin versionar; hoy se ha commiteado.

### El bug (core de Odoo 19, `addons/website`)

`website.get_current_website()` resuelve el dominio así:

```python
domain_name = (
    request and request.httprequest.host          # "host:puerto"
    or hasattr(threading.current_thread(), 'url')
    and threading.current_thread().url            # URL COMPLETA  <- el fallo
    or '')
```

El segundo término **no es un netloc**, es la URL entera. Ese valor llega sin tocar a
`_get_current_website_id()`, que hace `domain_name.encode("idna")`. El códec valida
**etiquetas** (los trozos entre puntos) de 63 caracteres como máximo:

```
http://localhost:8069/web/dataset/call_kw/website/configurator_apply
-> 68 caracteres, 1 etiqueta -> UnicodeError: label too long
```

Se dispara cuando `get_current_website()` corre **sin `request` enlazado**: cron y recargas de
registry (instalar o actualizar un tema). Deja inservible el configurador de sitio web en
cualquier despliegue servido desde un host sin puntos.

### ¿Hace falta el parche si hay dominio real?

Se midió contra el códec real en vez de razonarlo:

```
FALLA  etiqueta=68  http://localhost:8069/web/dataset/call_kw/website/configurator_apply
OK     etiqueta=49  https://tallervykia.es/web/dataset/call_kw/website/configurator_apply
OK     etiqueta=58  https://www.tallervykia.es/es/servicios/mecanica-rapida/cambio-de-aceite...
FALLA  etiqueta=64  https://tallervykia.es/web/dataset/call_kw/ir_module_module/button_immediate_install
OK     etiqueta=11  tallervykia.es
```

Conclusión matizada: con dominio real **casi siempre pasa**, porque se ganan los ~20 caracteres
de `http://localhost:8069`. Pero el límite se aplica al TLD pegado al path, así que un path
suficientemente largo sigue reventando.

Y hay un **segundo efecto silencioso**: cuando no falla, tampoco acierta. A
`_get_current_website_id` le llega la URL completa, que no coincide con ningún
`website.domain`, y el core cae al fallback:

```python
# website/models/website.py:1467
if not websites:
    if not fallback:
        return False
    return self.search([], limit=1).id   # <- el primer website que encuentre
```

Con un solo sitio web acierta por casualidad. Con dos, sirve el equivocado sin avisar.

> Precisión honesta: se demostró que **la cadena** de esa URL revienta el códec, no se capturó a
> Odoo generándola exactamente así. Escenario plausible, no observado.

### Decisión: commitear con `auto_install: False`

El manifest original llevaba `auto_install: True`. Se cambió a `False` **a petición explícita
del cliente**: este repositorio es el que irá a producción, y no quiere código de entorno de
desarrollo autoinstalándose en casa del cliente final.

Resultado: el módulo queda **versionado** (no se pierde en un clon nuevo, no hay que
rediagnosticar el bug) pero **inerte** en producción — un módulo no instalado ni siquiera se
importa. Se activa a mano en desarrollo.

Alternativas descartadas: no commitearlo (se pierde fuera de esta máquina) y commitearlo tal
cual (se autoinstala en producción sin decisión explícita).

**Aviso de despliegue:** en `taller` el módulo **sigue instalado**, porque se autoinstaló antes
del cambio y quitar el flag no desinstala nada. Si algún día se monta producción **restaurando
un dump de `taller`**, se llevaría el módulo instalado. Esa BD debe nacer limpia.

Se parchea la clase en tiempo de importación en lugar de heredar con `_inherit` a propósito: el
fallo ocurre mientras se reconstruye el registry, y ahí no hay garantía de que este módulo se
procese antes que el tema.

## 7. Personalización visual del backend

Encargo: que el ERP se vea más del taller y menos genérico. Solo el backend — la web pública se
deja al editor nativo.

### Qué hay y qué no

Community **no** trae sistema de temas de backend; eso es de Enterprise. Y el módulo clásico de
OCA para esto, **`web_company_color`, no está portado a 19.0** (comprobado en la rama `19.0` de
`OCA/web`: 38 módulos, ese no está).

La solución viene de fuera de OCA: **MuK IT**, LGPL-3, con rama 19.0 mantenida.

| Módulo | Versión | Depende de | Qué aporta |
|---|---|---|---|
| **`muk_web_colors`** | 19.0.1.0.9 | `web`, `base_setup` | Colores de marca, primario y de contexto |
| `muk_web_appsbar` | 19.0.1.1.12 | `web`, `base_setup` | Barra lateral + fondo por compañía |
| `muk_web_theme` | 19.0.1.4.9 | **6 módulos MuK** | Tema completo |

**Conflicto a tener presente:** `muk_web_theme` y `muk_web_appsbar` reescriben el menú de
aplicaciones, igual que `web_responsive` — que además lleva aquí un parche local. Meter el tema
completo obligaría probablemente a retirar `web_responsive` y con él su parche.

`muk_web_colors` no toca el menú, así que no colisiona. Por eso es lo único instalado.

### Lo instalado

`muk_web_colors` 19.0.1.0.9, vendorizado en **`addons_third/`** (carpeta nueva: MuK no es OCA y
mezclarlo en `addons_oca/` falsearía la procedencia). Montado como `/mnt/third-addons`.

Aporta 12 campos en *Ajustes → Ajustes generales → Colores*, en pares claro/oscuro — dos paletas,
una por modo:

```
color_brand_*     <- el color de la barra superior
color_primary_*   <- botones y acentos
color_info_*  color_success_*  color_warning_*  color_danger_*
```

Trae `i18n/es.po`, así que sale en español sin trabajo extra.

> **Gotcha:** al guardar colores Odoo regenera los bundles SCSS. Si no se ve el cambio es caché
> de navegador: `Ctrl+Shift+R`. Ver también la nota general de assets en el `CLAUDE.md`.

### El fondo del menú de aplicaciones

No lo pone ni el core ni MuK: lo pone **`web_responsive`**.

```scss
// web_responsive/static/src/components/apps_menu/apps_menu.scss
.o_grid_apps_menu[data-theme="milk"] {
    --app-menu-background:
        url("../../img/home-menu-bg-overlay.svg"),
        linear-gradient(to bottom, #{$app-menu-background-color}, ...);
}
.o_grid_apps_menu[data-theme="community"] {
    --app-menu-background:
        url("../../img/home-menu-bg-overlay.svg"),
        linear-gradient(to bottom, #{$o-brand-primary}, ...);
}

// legacy/scss/primary_variable.scss:5
$app-menu-background-color: rgb(233, 230, 249) !default;   // el lila por defecto
```

El tema es una **preferencia por usuario**, no una configuración global:

```python
# web_responsive/models/res_users.py:19
apps_menu_theme = fields.Selection([("milk", "Milk"), ("community", "Community")],
                                   default="milk", required=True)
```

**Solución adoptada (coste cero):** poner el tema en `community`. El degradado pasa a derivarse
de `$o-brand-primary`, que es justo lo que controla `muk_web_colors`, así que el fondo sigue
automáticamente al color de marca. Sin código.

### Vías si el cliente pide más adelante un fondo propio

Ninguna está hecha; quedan aquí documentadas para no reinvestigarlas.

1. **Color de fondo distinto del de marca.** `$app-menu-background-color` está declarado con
   `!default`, así que basta sobrescribirlo antes en el bundle `web._assets_primary_variables`.
   Módulo propio de ~15 líneas, sin tocar `addons_oca/`. Es la vía más limpia.

2. **Imagen propia (foto del taller, un coche…).** Sustituir
   `web_responsive/static/src/img/home-menu-bg-overlay.svg` **desde un módulo propio** que
   reemplace esa entrada del bundle de assets. Importante: no editar el fichero dentro de
   `addons_oca/` — es código de terceros y ya arrastramos un parche local ahí.

3. **Fondo configurable por compañía desde la interfaz.** `muk_web_appsbar`, que solo depende de
   `web` y `base_setup`. Ventaja: lo gestiona el usuario sin desarrollo. Inconveniente: añade su
   propia barra lateral y ahí sí puede chocar con `web_responsive`. Habría que probarlo en una BD
   desechable antes.

4. **Tema completo** (`muk_web_theme`): logo en la barra lateral, fondo por compañía, barra
   lateral dimensionable y mejoras de móvil. Arrastra 6 módulos y obliga a decidir qué pasa con
   `web_responsive`.
