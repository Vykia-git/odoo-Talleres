## 2. Marco normativo: los plazos reales

VeriFactu **no es obligatorio todavía**. El **Real Decreto-ley 15/2025, de 2 de diciembre**
(BOE de 3-dic-2025) aplazó **por segunda vez** la entrada en vigor del RD 1007/2023.

| Obligado | Fecha límite de adaptación del SIF |
|---|---|
| Sujetos al **Impuesto sobre Sociedades** | **1 de enero de 2027** |
| **Resto** de obligados (autónomos / IRPF) | **1 de julio de 2027** |

El periodo anterior a esas fechas es, en palabras de la propia AEAT, un **periodo de pruebas**:
se pueden remitir registros de prueba con un SIF en modalidad VERI\*FACTU y seguir facturando
con otro SIF hasta la fecha límite.

Lo que sí venció es la obligación de los **productores de software** (9 meses desde la Orden
HAC de 29-jul-2025), que aplica a Odoo S.A., no al taller.

Quedan **excluidos** los obligados a **SII** y los territorios forales con TicketBAI.

**Pendiente de dato:** si el taller es **SL** → enero 2027; si es **autónomo** → julio 2027.

Fuentes:
- [AEAT — Nota informativa: ampliación del plazo de adaptación de los SIF](https://sede.agenciatributaria.gob.es/Sede/iva/sistemas-informaticos-facturacion-verifactu/nota-informativa-ampliacion-plazo-adaptacion-facturacion.html)
- [BOE-A-2025-24446 — Real Decreto-ley 15/2025](https://www.boe.es/buscar/doc.php?id=BOE-A-2025-24446)

**Regla derivada:** la fecha de obligatoriedad se ha movido dos veces. No afirmarla de memoria
en ninguna sesión futura; verificar contra la AEAT.

### El módulo puente del TPV

`l10n_es_edi_verifactu_pos` (`depends: l10n_es_edi_verifactu, point_of_sale`) **no aplica**: el
taller no cobra por caja registradora, factura contra `account.move`. Existe porque el TPV
genera `pos.order` y contabiliza al cerrar sesión, mientras que VeriFactu exige registrar cada
emisión en el momento.

**Cuidado:** lleva `auto_install: True`. Si algún día se instala `point_of_sale`, el puente
aparecerá solo. Hoy `point_of_sale` está desinstalado, así que no se activó.

## 6. Deuda de la sesión del 17-sep: el bug IDNA del configurador web

Se quedó sin documentar. El código estaba en el árbol sin versionar; hoy se ha commiteado.

### El bug (core de Odoo 19, `addons/website`)

`website.get_current_website()` resuelve el dominio así:

```python
domain_name = (
    request and request.httprequest.host          # "host:puerto"
    or hasattr(threading.current_thread(), 'url')
    and threading.current_thread().url            # URL COMPLETA  <- el fallo
    or '')
```

El segundo término **no es un netloc**, es la URL entera. Ese valor llega sin tocar a
`_get_current_website_id()`, que hace `domain_name.encode("idna")`. El códec valida
**etiquetas** (los trozos entre puntos) de 63 caracteres como máximo:

```
http://localhost:8069/web/dataset/call_kw/website/configurator_apply
-> 68 caracteres, 1 etiqueta -> UnicodeError: label too long
```

Se dispara cuando `get_current_website()` corre **sin `request` enlazado**: cron y recargas de
registry (instalar o actualizar un tema). Deja inservible el configurador de sitio web en
cualquier despliegue servido desde un host sin puntos.

### ¿Hace falta el parche si hay dominio real?

Se midió contra el códec real en vez de razonarlo:

```
FALLA  etiqueta=68  http://localhost:8069/web/dataset/call_kw/website/configurator_apply
OK     etiqueta=49  https://tallervykia.es/web/dataset/call_kw/website/configurator_apply
OK     etiqueta=58  https://www.tallervykia.es/es/servicios/mecanica-rapida/cambio-de-aceite...
FALLA  etiqueta=64  https://tallervykia.es/web/dataset/call_kw/ir_module_module/button_immediate_install
OK     etiqueta=11  tallervykia.es
```

Conclusión matizada: con dominio real **casi siempre pasa**, porque se ganan los ~20 caracteres
de `http://localhost:8069`. Pero el límite se aplica al TLD pegado al path, así que un path
suficientemente largo sigue reventando.

Y hay un **segundo efecto silencioso**: cuando no falla, tampoco acierta. A
`_get_current_website_id` le llega la URL completa, que no coincide con ningún
`website.domain`, y el core cae al fallback:

```python
# website/models/website.py:1467
if not websites:
    if not fallback:
        return False
    return self.search([], limit=1).id   # <- el primer website que encuentre
```

Con un solo sitio web acierta por casualidad. Con dos, sirve el equivocado sin avisar.

> Precisión honesta: se demostró que **la cadena** de esa URL revienta el códec, no se capturó a
> Odoo generándola exactamente así. Escenario plausible, no observado.

### Decisión: commitear con `auto_install: False`

El manifest original llevaba `auto_install: True`. Se cambió a `False` **a petición explícita
del cliente**: este repositorio es el que irá a producción, y no quiere código de entorno de
desarrollo autoinstalándose en casa del cliente final.

Resultado: el módulo queda **versionado** (no se pierde en un clon nuevo, no hay que
rediagnosticar el bug) pero **inerte** en producción — un módulo no instalado ni siquiera se
importa. Se activa a mano en desarrollo.

Alternativas descartadas: no commitearlo (se pierde fuera de esta máquina) y commitearlo tal
cual (se autoinstala en producción sin decisión explícita).

**Aviso de despliegue:** en `taller` el módulo **sigue instalado**, porque se autoinstaló antes
del cambio y quitar el flag no desinstala nada. Si algún día se monta producción **restaurando
un dump de `taller`**, se llevaría el módulo instalado. Esa BD debe nacer limpia.

Se parchea la clase en tiempo de importación en lugar de heredar con `_inherit` a propósito: el
fallo ocurre mientras se reconstruye el registry, y ahí no hay garantía de que este módulo se
procese antes que el tema.
